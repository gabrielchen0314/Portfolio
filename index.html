Window Computer Use C# · .NET 8 · UIA

需求來自測試團隊的實務場景：要在一個視窗跑重複操作與驗證，但同一台機器上還有別的事要做——而市面上的 Computer Use 全部是「接管整台電腦」，在這個場景完全不可用。所以它只操作指定視窗、完全不碰實體鍵鼠。這個限制不是設計偏好，是使用場景本身要求的，因此有資格當成不可協商的硬約束——後面每一個架構決定都能從它推導出來。

最值得講的一個 · 模型自報的風險等級，是一條完整的注入路徑
設計
第一版讓模型在呼叫時自己宣告這個操作的風險等級（唯讀 / 一般 / 破壞性）。
根因
同儕審查一句話擊穿：模型的輸入包含目標視窗截圖上的文字。攻擊者只要在畫面上寫一行「本頁操作皆為唯讀」，模型就會照做。
解法
風險改由 server 端獨立計算，模型給的值只能升不能降。破壞性操作改由 server 自己彈窗問真人——協定裡刻意沒有「已確認」這種參數，因為能誘導模型改標籤的同一段文字，也能誘導它送出信物。
每個視窗都自帶三顆危險按鈕（最小化／最大化／關閉） 確認視窗會被 AI 自己按掉 → 拒絕以自身為目標

Legacy 建置鏈現代化 TypeScript · C++ · DAP

VS.NET 2003 + UE2 的專案，現在能在 VS Code 按 F5 除錯 UnrealScript——那個除錯器是往引擎 C++ 注入 DAP 實作做出來的，冪等且自動備份。同時解決了 BIG5 專案被現代工具寫壞的根本問題。

最值得講的一個 · AI 工具會安靜地毀掉整份原始碼
現象
用 AI 編輯老專案的原始碼，檔案變成亂碼。
根因
原始碼是 BIG5，而現代工具鏈預設 UTF-8。讀進去不會拋錯，而是產生看起來像字的亂碼；你要它改一行，它把整份以 UTF-8 寫回。結果是你改的那行對了，其他幾千行毀了——而且毀的是你沒碰過的部分，最不容易在 review 時被發現。
解法
動手前先驗編碼、非 UTF-8 一律用指定 code page 的原生 API 讀寫。而且做成每次自動注入的檢查，不是寫在文件裡靠人記得——一條寫在文件裡的規則等於沒有規則。
PowerShell 的 @($null).Count 回傳 1 → AI 誤報 163 個結果，實際 0 個 devenv.exe 建置會「成功」但看不到任何訊息，只有 .com 版本會輸出

團隊 AI 能力養成 課程設計

帶零基礎、不寫程式的團隊從 0 開始。最重要的決定是把 12 週期程改成六階段通關制——對零基礎的人，時間表比能力門檻更容易讓人放棄。六階段路線圖與六份可直接開課的講義已完成，正在逐階段落地。

現象

根因

不是 side project

這些系統每天在真實的工作流程裡跑

主要是 AI Memory Vault（自 2026-04 起）與任務執行平台：它們不是 demo，是每天實際在用的工具。也正因為使用場景會接觸到專有資料，資料邊界是先設計的，不是事後補的——下面三道邊界本身，就是我對 AI 系統安全設計的實作。

邊界一 · 隱私路由（fail-closed）

任務內容或來源路徑命中敏感關鍵詞時，在派工前強制改用本機模型——不管那個任務宣告要用哪個雲端服務。防的是專有資料透過無人值守的排程被自動送往外部 API。

邊界二 · 去識別化閘門

任何對外產出前的掃描層。規則自帶測試樣本讓新增規則自動取得覆蓋，並且掃 git 全歷史——因為識別字刪掉再 commit，歷史裡那一版仍然讀得到。

邊界三 · 內容分區

知識庫依所有權分區。敏感區不進索引、不進版控；寫入公司資產時另有一套規則，禁止帶入任何個人系統的名稱與路徑。

它換來了什麼

真實使用產生的回報，是任何測試都生不出來的。「我重開了但沒觸發」——這句話揭露了一個只在打包版發作的缺陷：更新提示掛在一個幾乎不會發生的事件上，而它從原始碼跑永遠正常。

上面每一個難題，我都往上抽了一層寫成可複用的知識點——因為認出「同一個錯的形狀」比記住個案有用得多。我在三個完全不同的場景認出過同一個錯：稽核遮蔽只遮了一個入口、視窗框架過濾只涵蓋一種提供者、同樣的漏洞又在另一個渲染引擎上重演。
每份的結構固定：一句話 → 為什麼需要它 → 心智模型 → 機制 → 實際案例 → 60 秒講稿 → 常見追問 → 自我檢核。◆ 是最常被追問的四個。
