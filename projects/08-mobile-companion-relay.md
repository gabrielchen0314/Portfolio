# 08 · 手機對端遊的伴隨 App 與中繼伺服器

> **讓手機登入一款 PC 端遊的帳號，中間隔著一台自己寫的中繼。**
> Unity · Lua · C#（WinForm 中繼伺服器）· TCP
> 2023-08 ~ 2023-12（之後零星補修）

> ⚖️ 歸屬：職務中開發，著作權屬雇主。本文記錄的是技術問題與解法，不是所有權主張。
>
> 📌 本文為去識別化版本，不含僱主、產品名稱、內部協定編號、工單號與路徑。

## 一、解什麼問題

公司有幾款營運多年的 PC 端遊。玩家想在手機上看自己的角色、裝備、武功，以及儲值。

直覺的做法是讓手機直接連端遊的遊戲伺服器，但走不通：

| 限制 | 原因 |
|---|---|
| 遊戲伺服器只認 PC 客戶端 | 登入流程、封包格式、連線管理都是為 PC 寫的，改它等於動到線上營運中的核心 |
| 協定字串是 BIG5 | 手機端執行環境預設只有 Unicode 系列編碼 |
| 手機會隨時消失 | 切到背景、被滑掉、換網路。PC 客戶端很少這樣斷，伺服器的斷線處理不是為這種節奏設計的 |
| 要上架雙平台 | 審核人員需要能登入的帳號，但端遊帳號有驗證碼等額外步驟 |

所以做法是三端：**手機 App，經過中繼伺服器，再到既有的端遊伺服器**。端遊伺服器只做最小變動，難的部分集中在中繼。

---

## 二、架構

```
手機 App（Unity + Lua）
  ├─ 一個殼，多款遊戲：每款遊戲一個模組資料夾
  │    切換遊戲時動態載入該遊戲的 Lua，離開時卸載
  ├─ 每款遊戲各自一份協定處理
  ├─ 心跳：連上中繼後自動送出
  └─ BIG5 / GB 解碼：載入 code page 提供者後統一經編碼常數表轉換
        │
        │  TCP，中繼專用的協定段
        ▼
中繼伺服器（C# WinForm）
  ├─ 連線對照表：記錄每個帳號用的是哪一條手機連線、接到哪一台遊戲伺服器
  ├─ 與遊戲伺服器的連線：斷線自動重連、重新讀取伺服器清單
  ├─ 登入閘：IP 國家過濾、人數上限、登入逾時、重複登入檢查
  ├─ 斷線翻譯：手機異常斷線 → 替它向遊戲伺服器補送登出
  └─ 儲值轉送：把手機端的儲值結果轉交給既有的儲值系統
        │
        ▼
既有端遊伺服器（不改核心，只認中繼這個入口）
```

我兩端都寫：App 端的協定、心跳、斷線處理、編碼與多遊戲切換，以及中繼伺服器的大部分程式。中繼的程式骨架沿用公司既有的登入閘道，轉送、連線對照、斷線翻譯與儲值轉送是這次加上去的。

## 三、開發難題與解法

### 難題 1：手機被滑掉之後，遊戲伺服器以為人還在線上

現象：玩家把 App 從背景滑掉，再打開，登不進去，提示帳號重複登入。

根因：遊戲伺服器的「在線」是看它和中繼之間的連線狀態。手機斷了，但中繼和遊戲伺服器之間的連線還好好的，**伺服器沒有任何理由認為這個玩家走了**。下一次登入就撞上「這個帳號已在線上」。

PC 客戶端很少遇到這個問題，因為 PC 斷線時伺服器直接看得到 socket 關閉。中間多一層中繼，這個訊號就被吃掉了。

解法：中繼是唯一同時看得到兩邊的位置，所以斷線的語意要在這裡翻譯。

```
手機連線中斷時:
    若 這條連線已登入成功 且 斷線原因是網路異常:
        組一個登出封包（帶上該帳號的識別資訊；需要驗證碼的伺服器一併帶上）
        以這位玩家的身分送給遊戲伺服器
    清除連線對照表中的紀錄
```

配套是心跳。手機被滑掉時不一定會正常關閉 socket，中繼要靠心跳逾時才知道它死了。所以 App 改成連上中繼就自動開始送心跳，後來又縮短了間隔，讓「人已經走了」更早被發現。

> 這是一個**沉默的失敗**：沒有例外、沒有錯誤 log，每一層都正確執行了自己的邏輯。錯的是層與層之間少了一句話。
> 加了一層轉送，就要回頭問一次：原本靠「直接看得到」傳遞的訊號，現在誰負責傳？

→ 知識點：沉默的失敗

### 難題 2：登入失敗時，先斷線再通知，手機永遠收不到原因

現象：密碼打錯之後，App 沒有顯示錯誤，而是卡住或直接斷線；換一支手機登同一個帳號也登不進去。

根因：中繼處理遊戲伺服器的登入結果時，順序是：

```
依結果處理:
    失敗 → 切斷這支手機的連線
把結果轉送給手機     ← 這時連線已經沒了
```

失敗分支先把連線切掉，後面的轉送送到一條已經不存在的連線上。

解法是把順序對調：**先轉送結果，再依結果動作**。改動只有幾行，但規則可以帶走：

> 「告知」要排在「切斷」之前。凡是會終結對方的動作，先確認對方已經拿到它需要的最後一則訊息。

同一批還修了重複登入時的清理：同一個帳號從第二支手機登入，要把舊的連線一併清掉，不然連線對照表會留下一筆指向死連線的紀錄。後來再擴充成跨多台遊戲伺服器的重複登入檢查。

---

### 難題 3：手機端解不開 BIG5

現象：協定裡的角色名稱、物品名稱在手機上變成亂碼，或在轉換時直接拋例外。

根因：端遊的協定字串是 BIG5（code page 950），簡中版是 GB（936）。手機端的 .NET 執行環境預設只帶 Unicode 系列編碼，要用 950、936 必須另外載入 code page 提供者並註冊。

解法：

1. 加入 code page 提供者，在啟動與網路模組初始化時註冊。
2. Lua 端把編碼收斂成一張常數表（繁中、簡中、各種 Unicode），所有轉換都經過同一個介面，不再散落魔術數字。
3. 字串轉位元組時對空字串防呆並記錄，避免一個空值在封包組裝時才炸開。

> 編碼問題在這個部門是固定班底：PC 端遊、伺服器、手機三個環境對「預設編碼」的認知都不一樣。
> 我後來在 AI 工具鏈上處理的 BIG5 寫壞問題（見專案卷 05），根源是同一件事。

→ 知識點：Legacy 編碼與工具鏈

### 難題 4：一個外部 HTTP 呼叫，可以拖垮整台中繼

現象：測試期間儲值相關的 HTTP 呼叫偶爾失敗。

根因：中繼把儲值結果轉交給既有儲值系統時，用的是同步 HTTP 呼叫，沒有例外處理。對方逾時或回錯誤時，例外會沿著封包處理流程往上冒，而**同一個行程裡承載的是所有在線玩家的連線**。一個人的儲值失敗，風險範圍是全部人。

解法：把外部呼叫包在例外處理裡，失敗時記錄並讓其他流程繼續。

這裡要誠實講代價：改完之後，失敗只會留在 log。依我現在的標準，這還沒寫完，因為「這段失敗了誰會知道」的答案是「去翻 log 的人」。該補的是告警或對帳端的補償，這是我回頭看最想重做的一處。

→ 知識點：沉默的失敗

---

### 難題 5：上架審核要的帳號，跟端遊的登入流程不相容

審核人員需要一組可以直接登入的帳號，但端遊帳號在某些伺服器需要驗證碼，部分帳號還被限制只能從 PC 登入。

做法是在 App 端與中繼端都辨識審核用帳號，讓它走一條簡化的路徑。這段沒有技術深度，但它是「從零做到上架」裡一定會碰到、而且只能在最後一個月才碰到的事。
