# 04 · Jarvis Core / Dashboard

> **一個刻意寫得很薄的核心，加上三個用 JSON Schema 契約掛進來的消費端。**
> Python（kernel）· TypeScript / Node 原生（dashboard）· JSON Schema
> 2026-07 起｜kernel 142 tests、dashboard 87 tests｜kernel ≤1500 LOC（**機器強制**）

---

## 一、解什麼問題

我已經有三個系統：知識庫、執行平台、還有一堆排程。它們各自能跑，但沒有一個地方能回答「**現在整體狀況如何**」。

直覺的作法是找一個既有系統當中心，把其他的接進去。**但那會讓那個系統長成一個什麼都做的大球。**

所以定位反過來：

> **「賈維斯是架構，大腦是元件。」**
> 核心只負責產出決策，不執行、不投遞、不長業務邏輯。其他系統以**消費端**的身分掛進來，大腦可換可升級。

---

## 二、架構

```
拓撲 2 + 1 + 1

  Vault / AI Engine     知識與 skills（消費端 1）
  jarvis-core           thin kernel：掃描 → 產出 redacted 決策，不執行
        │  contracts/*.schema.json（語言中立的檔案介面）
        ├─→ RATP                  安全執行與投影（消費端 2）
        └─→ jarvis-dashboard      本機觀測與操作入口（消費端 3）
```

### 兩條鐵則，都由機器強制

| 鐵則 | 強制方式 |
|---|---|
| kernel 不長業務邏輯 | **≤1500 LOC 的機器檢查**、import 規則、禁止呼叫 LLM |
| dashboard「有 UI 沒權限」 | **不配置任何具寫入能力的工具**——讓「旁路」在結構上不可能，而不是靠紀律 |

第二條是我最滿意的一個設計。權限不是用檢查擋住的，是**根本沒給**。

### 契約的驗證方式

消費端把契約 vendor 進自己的 repo 並 pin 版本。契約測試除了比版本號，還**逐 byte 比對 blob sha**——

> 抓的是「有人手改了 vendored 副本」。那種改動永遠回不到上游，只會讓兩邊悄悄分岔。

→ 知識點：**契約驅動解耦**

### 為什麼第三個消費端故意用 TypeScript

契約宣稱自己是「語言中立的檔案介面」。**一個宣稱要有證據。** 用異語言寫一個消費端，順帶證明它不是「只有 Python 讀得動的約定」；也讓「複製解讀邏輯過來」在物理上更麻煩。

## 三、開發難題與解法

### 難題速查

| # | 難題 | 根因形狀 | 知識點 |
|---|---|---|---|
| 1 | 一個穩定期閘門兩度失敗 | 它量的是「使用」，不是「健康」 | **沉默的失敗** |
| 2 | 對帳表自己就是不可信的來源 | 同一份文件兩處相反 | — |
| 3 | 契約凍結的「實證」其實什麼都沒證明 | fixture 是照 schema 寫的 | **契約驅動解耦** |
| 4 | 去識別化測試是綠的，但真的洩漏了路徑 | 測試 helper 用相對路徑 | **透過真實入口驗證** |
| 5 | 兩台機器的閘門狀態靜靜分岔 | 啟用狀態綁在被 gitignore 的檔案 | **沉默的失敗** |

---

### 難題 1 — 一個穩定期閘門兩度失敗，而它的設計本身是錯的

**規則**：某個功能要解鎖，必須先「連續 7 天穩定運行」。判準是稽核記錄裡有連續 7 天的對應事件。

**第一次失敗**：驗收日去查，7 天為 0。
**第二次失敗（換一台機器）**：再查，還是 0。

第二次之後我才看出**閘門本身的設計缺陷**：

> `entry_type=dashboard` 是**使用紀錄，不是健康紀錄**。
> 一個活著但沒人開的 dashboard，跟一個死掉的 dashboard，在這份稽核裡是**完全相同的零筆**——閘門分不出來。

於是「七天穩定期」實際要求的是「連續七天有人天天去點它」，而**沒有任何機制提醒人去點**。

**混淆因素已排除**：同期間其他入口每天都有寫入（cli 457 筆、discord 226 筆），檔案沒有斷檔。所以不是 log 掉了，是那個入口**七天零流量**。

**裁示不是「凍結」也不是「原判準重新起算」，而是改判準**：加一條每日自動 dry-run 心跳，讓「活著」自己留下證據。

而且心跳有三個必要條件，缺一個就只是把缺陷換個位置：
1. 心跳**必須真的走那個入口**（走別的入口不會產生對應事件，等於白做）
2. 要有排程真的觸發它
3. **心跳自己也要能被發現壞掉**——否則只是把「沒人用」換成「心跳沒跑」

> **在改判準之前重新起算，只是再等一次同樣的七天。**

---

### 難題 2 — 對帳表自己就是不可信的來源

消費端登記表的**表格與說明**寫著閘門已達成，**頁尾**卻仍寫「已登記消費端 1 個（目標 ≥2）」。

同一份文件兩處相反。**規劃時讀到哪一處，就得到哪個結論**——某次路線圖初稿正是據此把「補閘門」誤寫成開案動機，直到同儕審查去讀原始文件才抓出來。

> **改表格時要連敘述一起改**，否則對帳表自己就成了不可信的來源。

---

### 難題 3 — 契約凍結的「實證」其實什麼都沒證明

**閘門原文**：定契約前先累積 ≥20 則**真實** payload 樣本。

**當時的作法**：契約同步測試驗兩份**手寫 fixture**（一正一反），綠燈。

**問題**：fixture 是照著 schema 寫的。

> 它綠燈只證明 **schema 自我一致**，不證明**實際產出的東西合格**。
> 多欄位、少必填、列舉值打錯字——全都看不見。

**解法**：拿 **963 則真實 payload** 逐則過 schema，**0 則不合**。並且把這個一次性驗證變成常駐守門。

三個實作決定：
- 沿用既有的檔案讀取函式，不自己 glob（自己 glob 會連備份檔一起吃）
- 乾淨 clone / CI 環境沒有 runtime 資料時 **skip 而非 fail**——那條閘門量的是本機累積量，硬 fail 只會逼人把它關掉
- **突變驗證**：注入一則缺欄位的 payload → 指名「1/964 不合」；把樣本砍到 5 則 → 門檻斷言觸發。**兩條都真的會咬。**

---

### 難題 4 — 去識別化測試是綠的，但它真的洩漏了機器路徑

**現象**：頁尾洩漏了本機絕對路徑。而「不含機器路徑」的測試**是綠的**。

**根因**：測試 helper 用的是相對路徑，真實設定裡的變數展開後是絕對路徑。測試從來沒有走過會出事的那條路。

**處置順序值得記**：

> **先改測試讓它如實變紅，再修程式碼。**

反過來做（先修碼再看測試綠）證明不了任何事——你不知道那個綠燈是因為修好了，還是因為它本來就不會紅。

---

### 難題 5 — 兩台機器的閘門狀態靜靜分岔

**現象**：A 機器上啟用的功能，B 機器上從來沒啟動過，而且沒有人發現。

**根因**：啟用狀態寫在一個**被 gitignore 的設定檔**裡。

於是：
- 它不隨 git 同步
- 它**不被 `git status` 涵蓋**——工作區看起來永遠是乾淨的

**這件事的一般化**：被 gitignore 的設定不只是「不同步」，是**連「不同步」這件事本身都不可見**。凡是「行為的開關」放在這種檔案裡，就必須有另一個管道讓人查得到它現在是什麼值。

**衍生的一個決策**：跨機器彙總視圖**不是同步 runtime 資料**（那是各機器自己的健康狀態，合併就沒意義），而是讓每台把**摘要**寫進共用的知識庫目錄、面板讀全部機器。理由是那是兩台之間**唯一已在運作的共用通道**，各機寫各機目錄不會衝突。

## 四、幾個值得記錄的技術決策

| 決策 | 結論 | 理由 |
|---|---|---|
| 前端形態 | Node 原生 TS 伺服器渲染，**零建置**（偏離原規格的 React/Vite） | Dashboard 的存在意義是「系統壞掉時看得見」，而**建置步驟是一個會在最需要它的時候失敗的環節**。互動需求約 20 行原生 JS |
| 人格層 | persona **只在渲染層**，純函式，可一鍵切素面模式 | 可驗證的定義是「砍掉 persona renderer，系統照常運作」 |
| 動作預設 | `enabled=false`（不開埠）+ `live_commands=[]`（全 dry-run） | **一個預設是開的安全開關不是開關，是裝飾** |
| 去重鍵 | 秒級 mtime → **內容雜湊** | 同秒兩次修改在原設計會被判定為同一筆而**永久漏掉**。雜湊才是「兩筆真的相同」而不是「時間戳巧合相同」 |
| 已見集合 | 從投遞紀錄**自身重建**，不另存狀態 | 另存一份狀態就會漂移 |
| worker 存活判定 | **OS 檔案鎖**，不用 pid 比對 | Windows 上 `os.kill(pid,0)` 會真的殺掉行程；pid 檔躲不掉殘鎖與重用；檔案鎖在崩潰時由核心自動釋放 |

**規格偏離的處理方式**：實作採用了與規格不同的技術棧，我在規格書的「實作回饋」段記錄了偏離與理由，**未竄改規格原文**。

> 規格與實作不一致時，正確的動作是留下兩份並說明，而不是把歷史改成「我一開始就這樣想」。
