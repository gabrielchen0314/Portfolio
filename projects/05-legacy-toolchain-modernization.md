## 一、解什麼問題

有一類專案在業界很常見，但幾乎沒人寫它。還在賺錢、還在改，但工具鏈停在二十年前。

具體長這樣：

- 編譯器是 Visual Studio .NET 2003（MSVC 7.1）
- 遊戲引擎是 Unreal Engine 2，腳本語言 UnrealScript
- 原始碼編碼是 BIG5（code page 950），不是 UTF-8
- 版本控制殘留 SourceSafe 時代的 `vssver2.scc` 檔

這種環境的真正成本不是「舊」，是它把所有現代工具擋在門外：

| 想用的東西 | 為什麼用不了 |
|---|---|
| VS Code 的編輯體驗、IntelliSense | 專案是 `.vcproj`，不是現代格式 |
| 現代除錯器 | UnrealScript 的除錯只有 Epic 官方的獨立工具 |
| **AI 輔助開發** | AI 工具預設 UTF-8，直接讀寫會**寫壞檔案** |

最後一條是關鍵。這個專案真正的價值不是「讓老專案能在 VS Code 開」，是：

> **讓一個 2003 年的專案，能被 2026 年的 AI 工具安全地讀寫。**

## 二、做了什麼

一個 VS Code Extension，把整條鏈接起來：

```
VS Code（前端 IDE）
   ├─ 初始化：掃描工作區 → 產生 build.bat / tasks.json / launch.json / c_cpp_properties.json
   ├─ 建置：vsvars32.bat 初始化環境 → devenv.com 建置
   │        錯誤自動進 Problems 面板，可點擊跳轉原始碼
   ├─ C++ 除錯：cppvsdbg 附加至遊戲行程，支援 .pdb 與中斷點
   └─ UnrealScript 除錯：兩種模式
        ├─ 模式一：同步中斷點到官方除錯器的 INI 後啟動它
        └─ 模式二：★ 原生 DAP —— 直接在 VS Code 下中斷點
```

整個流程約 30 秒，新專案只需重複 5 個步驟。

### ★ 模式二：自己實作 UnrealScript 的 Debug Adapter

這是這個專案技術含量最高的部分。

UnrealScript 沒有現成的 DAP 實作。所以往引擎的 C++ 原始碼裡注入一個 DAP server。

一鍵指令自動完成四件事。以虛擬碼描述：

```
於 引擎核心模組:
    新增 DAP server 實作（C++）
    加入該模組的專案參考

於 啟動模組:
    注入 除錯器初始化()   ← 程式啟動時
    注入 除錯器關閉()     ← 程式結束時

於 視窗驅動模組:
    修補型別轉換，避免除錯器附加時崩潰
```

所有修改具冪等性，重複執行不會重複注入，並自動備份原始檔案。

> 冪等性在這裡不是潔癖。這個指令會被不同的人、在不同的機器、對同一份原始碼跑很多次。
> **一個非冪等的注入器，第二次執行就會產生一份編不過的原始碼，而且沒有人知道是誰弄的。**

另外附一個「引擎已知問題修正」指令，修掉兩個歷史缺陷。一個是啟動參數被誤判為地圖名稱，一個是空指標崩潰。

## 三、開發難題與解法

### 難題 1 — AI 工具會寫壞 BIG5 檔案，而且不會報錯

現象：用 AI 編輯老專案的原始碼，檔案變成亂碼。

根因：現代工具鏈預設 UTF-8。讀取一個 BIG5 檔案時，它不會拋錯，而是產生看起來像字的亂碼（`瑭檢`、`庛?` 這類），然後你要它改一行，它把整份以 UTF-8 寫回。

> **這是沉默失敗的完美標本**：沒有例外、沒有紅字、檔案還在，只是內容毀了。
> 而且毀掉的是你沒有改到的那些行。你改的那行是對的，其他幾千行變成亂碼。

解法是一條硬規則，寫進所有 AI 工具的全域設定：

1. 編輯任何檔案前先確認原始編碼
2. 內容出現亂碼就是非 UTF-8
3. 非 UTF-8 檔案禁用一般的讀寫工具，改用指定 code page 的原生 API

```powershell
# 讀取
$content = [IO.File]::ReadAllText($path, [Text.Encoding]::GetEncoding(950))
# 寫回（保持原始編碼）
[IO.File]::WriteAllText($path, $newContent, [Text.Encoding]::GetEncoding(950))
```

| 編碼 | Code Page |
|---|---|
| BIG5（繁中） | 950 |
| GBK（簡中） | 936 |
| Shift-JIS（日文） | 932 |

這條規則後來變成一個常駐的守門機制。不是靠人記得，是每次動手前自動注入的檢查。

### 難題 2 — `@($null).Count` 回傳 1，讓 AI 把 0 報成了滿滿一整批

現象：批次清理 SourceSafe 殘留檔並建立對應的合併請求。AI 回報整批都建好了。

**實際是 0 個。**

根因：PowerShell 的陣列包裝運算子對 `$null` 的行為：

```powershell
@($null).Count   # → 1   ❗ 不是 0
@().Count        # → 0
```

API 回傳空結果時是 `$null`，包成陣列後 `.Count` 是 1。迴圈每跑一個分支就「數到 1 個」，於是全部都被記成有結果。

解法：改用原始的 HTTP response body 直接判斷，`[]` 代表真的 0 筆。

教訓不是「記住這個 PowerShell 陷阱」，是：

> **計數是一種推論，不是觀察。**
> 當你要根據一個數字下結論時，先確認那個數字是數出來的，還是某個包裝行為的副產品。

同一族的還有：`git push` 逾時不等於沒推上去。後來查遠端發現其實成功了，卡住的是後面串的核對步驟。

### 難題 3 — 建置期的歷史地雷

這些不難，但它們是這類專案的日常，值得列出來說明「維護 legacy 的實際內容是什麼」：

| 症狀 | 根因 | 解法 |
|---|---|---|
| `LNK1201: error writing to .pdb` | 舊版連結器對 PDB 的鎖定行為 | 建置前清理 PDB（設定項，預設開） |
| 中文編譯訊息亂碼 | 終端機 code page 不是 950 | 可設定的 console code page |
| F5 跳出但不中斷 | 編譯選項是 `/ZI` 而非 `/Zi` | 明確要求 `/Zi` 並重新建置 |
| `devenv.com` 不是內部命令 | **必須是 `.com` 而非 `.exe`** | 設定項預設指向正確路徑 |

最後一條特別典型。`devenv.exe` 與 `devenv.com` 是兩個不同的執行檔，只有 `.com` 版本會把建置輸出送到標準輸出。**用錯的那個，建置會「成功」但你看不到任何訊息。**

### 難題 4 — AI 不採信使用者的直接觀察

這是一個互動層面的失敗，我把它留在這裡，因為它比技術問題更常發生。

使用者多次明確描述：「沒有彈窗、只有鈴鐺紅點，其他工具都會彈」。

AI（我）仍然一度堅持往命令面板、重新載入視窗的方向排查，造成來回耗時，直到使用者說「你要繼續浪費時間嗎」。

檢討：使用者描述的是畫面上正在發生的事實，那是第一手觀察。我拿的是對系統行為的推論。當兩者衝突時，**應該先採信觀察，去解釋它，而不是去否定它**。

> 這條後來變成我跟 AI 協作時的固定原則，也反過來要求我自己：
> **當現場證據跟我的模型衝突，錯的預設是我的模型。**
