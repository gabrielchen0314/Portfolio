# 07 · AI Memory Vault 從個人到團隊的落地路徑

> 主體是 [01 AI Memory Vault](01-ai-memory-vault.md) 這個 RAG 知識庫。
>
> **它的形狀從第一天就是多方協作的。「擴展成團隊共用」不是重新設計，是補上三個單人環境用不到的東西。**
> 本文是設計推導，不是承諾的 roadmap——每一項都標明「已驗證什麼」與「還缺什麼」。

---

## 為什麼可以這樣講

三個設計決定，當初的理由不是為了團隊，但它們的結果是團隊友善的：

| 當初的決定 | 當初的理由 | 對團隊的意義 |
|---|---|---|
| 知識用**純 Markdown + git**，不用資料庫 | Obsidian 可讀、grep 可搜、可版控 | **PR review 天然可行**，用的是團隊本來就熟的工具 |
| 系統間用 **JSON Schema 契約**，不用函式呼叫 | 防止核心長成大球 | **新增消費端不需要動核心**——已驗證 3 個 |
| 內容依**所有權**分區，不依可見性 | 出貨的規則要落地在使用者的知識庫裡 | 「哪些該共享、哪些該私有」這個判斷**已經做過了** |

> 這三件事如果當初做反了（資料庫、直接 import、單一命名空間），今天的答案會是「重寫」。

---

## 缺的三件事

### ① 共用的知識層

**已驗證的相鄰情境**：跨節點同步已經在運行，只是節點目前是**兩台機器**而不是兩個人。

**踩過的坑（直接適用於團隊）**：

| 坑 | 症狀 | 處置 |
|---|---|---|
| 自動提交的排程互相沖掉 | 一台機器的 commit 從遠端消失，`git log` 看不出來 | 排程要能查得出「誰在什麼時候推了什麼」；force push 必須可稽核 |
| 合併策略對結構化檔案的破壞 | union 策略對「行的集合」安全，對 JSON 會產出**語法不合法**的內容（兩段各自合法、相連之後解析直接失敗） | 結構化檔案不能套 union，要有型別感知的合併規則 |
| 被 gitignore 的設定讓兩端靜靜分岔 | A 機器啟用的功能 B 機器從沒啟動，而且 `git status` 永遠是乾淨的 | 行為開關不能只存在 gitignore 的檔案裡，要有另一個管道查得到現值 |

**還缺的**：把 remote 換成組織的 repo，並決定同步節奏（現在是排程自動提交，團隊環境可能需要改成顯式 push）。

---

### ② 寫入權限與審查流程

**現況**：單人直寫，沒有 review 環節。

**為什麼補起來很便宜**：知識是**純 Markdown 檔案**。一個團隊要加 review，只需要：

```
個人分支 → PR → review → merge
```

不需要新工具、不需要新權限模型、不需要教任何人新的操作。**這是當初選檔案系統而不選資料庫換來的。**

**還缺的**：決定哪些區域需要 review、哪些可以直寫。我的判斷是——

| 區域 | 是否需要 review | 理由 |
|---|---|---|
| 共用規則 | ✅ 需要 | 它會改變所有人的 AI 行為 |
| 專案狀態 / 工作日誌 | ❌ 不需要 | 那是紀錄，不是規範；加 review 只會讓人不寫 |
| 個人經驗卡片 | ❌ 不需要 | 個人的，本來就不共用 |

> 一個對所有寫入都要 review 的知識庫，會很快變成一個沒有人寫的知識庫。

---

### ③ 誰能看哪一區

**現況**：已經依所有權分三層——共用規則 / 個人經驗 / 敏感內容。敏感區**不進索引也不進版控**。

另有一道對外的去識別化閘門：規則自帶測試樣本（讓新增規則自動取得覆蓋），並且**掃 git 全歷史**——因為識別字刪掉再 commit，歷史裡那一版仍然讀得到。

**還缺的**：存取控制那一層。但要加的是 ACL，**不是重新切分內容**——內容的界線已經在那裡了。

---

## 三個我會提前講清楚的風險

如果真的要在一個團隊導入，這三件事我會在動工前先講：

1. **不要一次全開。** 先用一個小組、一個專案跑一段時間。理由不是保守，是——我自己的穩定期閘門失敗過兩次，而根因是**它量的是「使用」不是「健康」**。沒有真實流量的試行期，你量到的東西沒有意義。

2. **共用規則會改變所有人的 AI 行為，所以它的變更要當成程式碼改動看待。** 一條規則寫錯，影響範圍是每個人的每一次對話，而且**失敗是沉默的**——沒有人會收到告警。

3. **導入的阻力不在技術。** 我帶過零基礎團隊導入 AI，最重要的一個決定是把期程制改成通關制——因為對零基礎的人，時間表比能力門檻更容易讓人放棄。技術可以一週裝好，行為改變不行。

---

## 面試怎麼講

> 我這套系統現在是個人在用的，但它的形狀從第一天就是多方協作的——契約驅動、多消費端、依所有權分區。所以要變成團隊共用，缺的不是重寫，是三件單人環境用不到的東西：**共用的儲存層、寫入的審查流程、以及存取控制**。
>
> 而這三件我都已經踩過相鄰的問題。**跨節點同步我實作過也踩過坑**，只是節點目前是兩台機器不是兩個人——包括自動提交排程互相沖掉、以及合併策略對 JSON 這種結構化檔案會產出語法不合法的內容。
>
> 審查流程反而是最便宜的，因為知識是純 Markdown 不是資料庫，PR review 天然可行、不用教任何人新工具——**這是當初選檔案系統換來的**。
>
> 但如果真要在一個團隊導入，我會先講三件事：不要一次全開、共用規則的變更要當程式碼改動看待、以及**導入的阻力不在技術**。技術可以一週裝好，行為改變不行。
