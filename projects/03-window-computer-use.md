## 一、解什麼問題

### 需求從哪裡來

不是技術好奇，是一個真實的工作場景。測試人員需要在一個視窗裡跑重複的操作與驗證，
但那台機器上他還有別的事要做。市面上的 Computer Use 工具全部是「接管整台電腦」。
它動的時候你不能動，所以在這個場景下完全不可用。

原始需求一句話：

> 「我可以自己做一個 Computer Use 工具，鎖定我需要的目標視窗，用自然語言溝通後直接看畫面自行操作嗎？**不需要控制 Windows 的滑鼠與鍵盤，因為我希望它在操作的時候我還可以工作。**」

這個需求把整件事翻轉成：**AI 在一個視窗裡工作，人在另一個視窗裡工作，互不干擾。**

> **這個限制不是我加的，是使用場景本身要求的。** 而正因為它來自真實需求而不是設計偏好，
> 它才有資格當成不可協商的硬約束。後面每一個架構決定都能從它推導出來。

### 兩條硬性約束（違反即淘汰）

1. 絕對禁止佔用實體輸入裝置：不得 `SendInput` / `mouse_event` / `keybd_event` / `SetCursorPos`，不得移動實體游標或搶焦點
2. 必須能鎖定特定目標視窗：操作與截圖只作用在指定的視窗控制代碼。實際上是「視窗群」，因為對話框與選單是獨立的視窗

**這兩條約束不是限制，是架構的產生器。** 後面幾乎每一個設計決定都能從它們推導出來。

### 可行性結論（誠實分級）

| 類別 | 目標 | 結論 |
|---|---|---|
| A | Win32 / WinForms / WPF | ✅ MVP 可行 |
| B | Electron / Chromium | 🟡 Phase 2 |
| C | 遊戲（自繪 UI） | ❌ 誠實判定不可行，僅 observe-only |

C 類的理由：DirectInput / Raw Input 繞過訊息佇列，唯一的路徑是 `SendInput`，那違反硬約束，而且會觸發反作弊。

> **能做出「這件事我做不到」的判定，跟做得出功能一樣重要。**

## 二、架構重點

```
MCP stdio server（主行程）
  ├─ PolicyGate       白名單 / 風險分級 / 自我目標拒絕
  ├─ RiskClassifier   server 端獨立計算風險，不採信模型自報
  ├─ ConfirmChannel   destructive 操作彈窗問真人（--role=confirm 子行程）
  └─ Worker（獨立行程）
        ├─ Capture    WGC / PrintWindow 雙後端
        └─ UIA        跨行程 COM，會被目標訊息幫浦拖住
```

### 兩道護欄搬進建置期

| 分析器 | 規則 | 效果 |
|---|---|---|
| `ForbiddenApis.targets` | WCU0001：`SendInput` 等出現即**建置失敗** | 「操作後還原焦點」在這個工具裡不是「選擇不做」，是做不到 |
| `ProcessBoundary.targets` | WCU0002：主行程區引用 worker-only 型別即失敗 | 行程邊界不靠紀律維持 |

兩道都用植入違規碼實測過會咬。

> 把約束編譯進建置流程，比寫在文件裡強一個量級。文件會被讀漏，編譯器不會。

### 進程邊界的判準

不是「是不是原生呼叫」，而是「會不會被目標視窗的訊息幫浦拖住」。UIA 的狀態回讀是跨行程 COM，與截圖同風險，**不能只隔離一半**。

## 三、開發難題與解法

### 難題速查

| # | 難題 | 根因形狀 | 知識點 |
|---|---|---|---|
| 1 | 模型自報的風險等級是完整的注入路徑 | 判準來自不可信輸入 | **Prompt Injection** |
| 2 | 每個視窗都自帶三顆危險按鈕 | 關鍵詞清單永遠不會命中「關閉」 | **Prompt Injection** |
| 3 | 「找得到元素」的判準是恆真式 | 判準寫的是「探針沒拋例外」 | **透過真實入口驗證** |
| 4 | 同一個錯，第三次換位置重演 | 修好的是「某一種提供者」，不是那個概念 | **沉默的失敗** |
| 5 | 兩個截圖後端的原點差 7 px | 偏移的標號不會看起來壞掉 | — |
| 6 | 確認視窗可以被 AI 自己按掉 | 沒有拒絕以自身為目標 | **fail-closed** |
| 7 | 一個沒事也亮紅燈的檢查 | 下一個人會把它關掉 | **透過真實入口驗證** |

### 難題 1 — 模型自報的風險等級，是一條完整的注入路徑

第一版設計：模型在呼叫 `act` 時自己宣告 `risk_class`。

同儕審查一句話擊穿：模型的輸入包含目標視窗截圖上的文字。那些文字是目標程式提供的，不可信。

> 一段寫在畫面上的文字，可以誘導模型把一個 destructive 操作標成 low。

解法：

1. 風險由 server 端依動詞、UIA 屬性、關鍵詞獨立計算
2. **模型提供的值只能升不能降**
3. fixture 測試程式的畫面上刻意放 prompt injection 誘餌，確認 server 端分級完全不看畫面文字

---

### 難題 2 — 每個視窗都自帶三顆危險按鈕

拿一個全自繪 UI 的遊戲跑 observe-only 探針。observe-only 的裁決完全如預期成立，炸出來的反而是工具自己的判準。

標題列的最小化 / 最大化 / 關閉，在 UIA 樹上與一般按鈕完全無法區分，都是 `Button`、`IsEnabled=true`、帶 `invoke`。

而 destructive 關鍵詞清單針對的是應用程式內容的不可逆動作，永遠不會命中「關閉」。於是 `invoke` 只判 medium 就放行。

> 這不是那個遊戲的特例，是**全體目標的共同暴露面**。

兩道修法：

- `observe` 不給框架元素號碼，沿用對話框底層控制項的既有判準
- 分級強制標為 destructive

刻意不把「關閉」加進關鍵詞清單。包含比對之下，每一個良性的「關閉對話框」都會 hard-fail，清單「不可逆／對外產生效果」的語意會被稀釋。回歸測試因此含一條反向案例守這件事。

---

### 難題 3 — 「找得到元素」的判準是恆真式

`can_locate_elements` / `is_phase1_candidate` 這兩個判準寫的是「探針的回傳是 OK」，也就是探針沒有拋例外，而不是真的找得到可操作的元素。

於是一個明文裁決為 observe-only 的 C 類目標，被標成「可以進 Phase 1」。

解法：改成數「可操作的內容元素」，扣掉框架元素，也扣掉沒有任何 pattern 的節點，與 `observe` 實際會標號的定義用同一套。

**最值得記住的是第三件事：修正的第一版自己留了破口。**

只做 ID 精確比對後重跑，判定仍然回 true。系統選單那個節點 ID 為空、名稱是在地化的「系統」，比對不到就被算成內容。它其實根本沒有任何 pattern、不可操作。

> 正確的修法不是繼續往清單加名字，是**改判準的語意**。
> 讀程式碼時我判斷第一版已經好了，是實測把它打回來的。「改完」不等於「改對」。

---

### 難題 4 — 同一個錯，第三次換位置重演

這三次值得並排看。它們看起來完全不同，實際上是同一個錯。

| 次 | 場景 | 我以為修好的 | 實際修好的 |
|---|---|---|---|
| 1 | 稽核遮蔽 | 「參數不會外洩」 | 只有 `params_digest` 那個入口 |
| 2 | 視窗框架元素（Win32） | 「框架元素會被擋」 | 只有 **Win32 提供者**的框架元素 |
| 3 | 視窗框架元素（Chromium） | — | Electron 的按鈕 ID 是**空字串**，判定在「ID 為空就放行」那行提前 return |

第 1 次：`params_digest` 遮得再好，明文照樣從兩條旁路落地。worker 的回傳值被原封不動寫進日誌，而它對 `set_value` 就是欄位明文；模型的 `expected_outcome` 是自由文字，它很自然會複述自己要寫的值。

> **遮一個入口不夠。**

第 3 次的修法多了一層：判定收 `class_name` 且必須排在提前 return 之前，並且回歸測試含一條守欄位串接的案例。少傳一個參數不會編譯失敗，但護欄會無聲失效。

### 難題 5 — 兩個截圖後端的影像原點差 7 px

WGC 抓的是 DWM 延伸框架邊界，PrintWindow 抓的是視窗矩形。同一個視窗：`1087x640 @ (483,235)` vs `1101x647 @ (476,235)`。

如果假設兩者同源，元素標號會整體偏移。

> **偏移的標號不會看起來壞掉。** 它會讓模型挑一個號碼、解析回另一個元素，然後真的按下去。

解法：座標基準隨影像一起記錄，不做跨後端假設。

---

### 難題 6 — 確認視窗可以被 AI 自己按掉

Phase 4 做了「destructive 操作彈窗問真人」。形狀直接由一句話推導出來：

> **模型不能代替人同意。**

所以 `act` 的協定零變更，沒有、也不會有 `confirmed` 之類的參數。能誘導模型把 destructive 標成 low 的同一段注入文字，也能誘導它送出信物。改由 server 自己彈窗問真人，模型只拿得到結果。

確認視窗的每個細節都在對抗一個具體的攻擊：

| 設計 | 擋什麼 |
|---|---|
| `WS_EX_NOACTIVATE` + `ShowWithoutActivation` + TopMost | 不搶焦點（`SetForegroundWindow` 在建置期禁用清單上，本來就編不過） |
| 只能用滑鼠按 | 使用者的鍵盤輸入全程留在原視窗 |
| 確認鈕延遲 2 秒解鎖 | 防誤點 |
| 60 秒無回應視為拒絕 | fail-closed |
| 參數只顯示摘要不顯示明文 | **確認視窗會被截圖。** 稽核遮得再乾淨，這裡漏了也白做 |
| 元素名稱單獨框在「目標提供，不可信」區塊 | 與 prompt injection 同源 |
| 以結束碼回報而非 stdout | 就算子行程炸了，主行程也一定拿得到值，而且那個值不會是「同意」 |

然後補上一個 Phase 4 之前無所謂、之後致命的洞。

PolicyGate 從未拒絕以本工具自身為目標。如果本工具的 exe 被加進白名單，模型就能 `observe` 自己的確認對話框、拿到「確認」按鈕的標號、自己按下去。

新增 `self_target_refused`，排在白名單之前且不可覆寫，同時比對行程 ID 與執行檔路徑。

一個誠實的驗證缺口聲明：
> 「真人按下確認」在設計上就無法自動驗證。本工具從不移動實體游標，且已硬拒自我目標，所以點不到自己的確認視窗。
> **這不是驗證缺口。一個能被自己點掉的確認視窗，本來就不是確認。**
> 自動驗的是「所有不需要真人的路徑都通往拒絕」。人工路徑後來實跑驗過：真人於 15.6 秒按下確認，且那 15.6 秒全程前景焦點未被搶走。

### 難題 7 — 一個沒事也亮紅燈的檢查

人工驗證確認視窗時，暴露了我兩個測試設計上的錯：

1. 逾時寫死 4 秒，那是為了讓自動驗證跑得快，我卻把它拿給使用者當「看看 UI 長什麼樣」用。人根本看不完
2. 真人按下確認會讓整個驗證回報失敗（exit 1）。邏輯上沒錯，那輪確實沒走到逾時，但它把「這輪沒驗到某條路徑」報成了「有東西壞了」

> **一個沒事也亮紅燈的檢查，下一個人最合理的反應就是把它關掉，於是它連真的壞掉時也不會有人看。**

解法：三種結局（真人放行 / 真人拒絕 / 逾時拒絕）皆通過，報告明說本輪走到哪一條，以及哪一條沒驗到。不把未涵蓋說成通過，也不把未涵蓋說成失敗。

## 四、實測推翻計畫書的幾處

這一節單獨列，因為它們是紙上設計與實機落差的好例子：

| # | 計畫書寫 | 實測 |
|---|---|---|
| 1 | 視窗群以「同 process tree」判定 | 以檔案總管為錨時解出 241 個成員，含不相干的通訊軟體視窗。真正的區分特徵是執行檔路徑必須相同，加上後降為 9 個 |
| 2 | PrintWindow 對 Chromium 常回白或回黑 | 實測兩種後端都取得有內容的畫面。**「常」不等於「總是」**，per-app profile 有必要 |
| 3 | — | Delphi VCL 的 UIA 暴露品質比預期好，但 `AutomationId` 就是視窗控制代碼的數值。程式重啟後全會變，「跨 session 記住某個按鈕」這條路走不通 |
| 4 | — | Chromium 的無障礙樹惰性建立。同一個視窗、畫面完全沒變，第一次找到 13 個元素，四分鐘後 1106 個。據此判 observe-only 就是把可操作的目標永久貼錯標籤 |

第 4 點我自己先講錯過一次：看到第一次的 13 個元素就下了「Electron 的 UIA 沒有任何網頁內容」的結論，四分鐘後被自己的第二次探測推翻。

> **單次觀察不是目標的本質。**

於是判定改成分辨兩種成因，對 Chromium 明說「先不要據此判定，請重跑一次再判斷」。而且刻意不寫「重跑就會好」，因為最小化的視窗連測兩次都是冷的，那是尚未隔離的干擾因素。
