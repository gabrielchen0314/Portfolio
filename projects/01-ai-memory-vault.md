# 01 · AI Memory Vault

> **把個人知識庫變成 AI 的長期記憶。**
> Python · ChromaDB · LangChain · FastMCP · PyInstaller · Inno Setup · Tauri
> 2026-04 起，進行中｜2,397 tests / 12 skipped｜25 個 MCP 工具｜v4.2.x

---

## 一、解什麼問題

跟 AI 協作最大的浪費，是**每次都要重新解釋一遍脈絡**：我用什麼命名慣例、這個專案卡在哪、上次那個坑是怎麼解的。

市面上的作法是把知識塞進 prompt，但塞不下；或者做成 RAG 讓 AI 自己查，但 AI **不會主動想到要查**。

所以這個系統的定位不是「一個能搜的知識庫」，而是：

> **一個讓 AI 在對話開始的第一次呼叫就自動拿到對的脈絡的系統。**

知識以純 Markdown 存在檔案系統（Obsidian 可讀、grep 可搜、git 可版控），索引進 ChromaDB，透過 MCP 協定暴露成工具面給任何支援 MCP 的 AI 客戶端。

## 二、架構

### 五層堆疊

```
Transport   main.py 依 --mode 路由到 stdio / SSE / CLI
MCP Tools   mcp_app/tools/ — 25 個工具，15 個模組
Services    services/ — VaultService 門面、Scheduler、Instinct、Extractor
Core        core/ — Indexer、Retriever、Embeddings、VectorStore、Migrations
Config      config.py — AppConfig dataclass，從 DATA_DIR/config.json 載入
```

### 四種部署形態，同一份程式碼

| 形態 | 傳輸 | 用途 |
|---|---|---|
| Python venv | stdio MCP | 開發 |
| PyInstaller exe + Inno Setup 安裝檔 | stdio + SSE | 一般使用者（132 MB 安裝檔） |
| Docker | SSE (8765) | 遠端／跨機器 |
| Tauri 桌面 UI | HTTP → SSE | 進行中 |

**這個「四形態」是後面一整節難題的來源**——同一份程式碼在 frozen 模式下的行為，跟從原始碼跑不一樣，而測試只跑後者。

### 檢索管線

```
query
  ├─ BM25 稀疏檢索          權重 0.4
  └─ ChromaDB 向量檢索       權重 0.6
        ↓ 合併
   時間衰減重排（指數，半衰期 90 天）
        ↓
   top_k 結果
```

Embedding 模型 `paraphrase-multilingual-MiniLM-L12-v2`（多語、CPU 可跑）。
→ 知識點：**混合檢索**

### 一次往返拿完脈絡：`session_bootstrap`

冷啟動的 AI（SubAgent、外部工具）繼承不到主對話的記憶注入。原本要三次呼叫（派 agent → 查直覺 → 載 skill），改成單一工具回傳六個區塊：

導航與身分 / Agent 行為定義 / 經 scope 過濾的規則 / 高信心直覺 / 可用 Skill 清單 / 守門啟用狀態

**每個區塊獨立容錯**——單一來源失敗（例如向量索引壞掉）不影響其他區塊。
→ 知識點：**MCP 工具面設計**

### 控制平面 / 使用者資料分離（v3.26.0）

系統本身要出貨給人用，但出貨的內容（規則、目錄契約、hook 資產）會**落地在使用者的知識庫裡**，因為 Claude Code、Obsidian、grep 都得讀得到它。

問題是：使用者也可以編輯它。

解法是**切所有權，不切可見性**：

- 落地的檔案照樣是可讀的 `.md`
- 但**權威**在 `AI_Engine/control_plane/`，落地那份是可再生的投影
- 啟動時 reconciler 比對投影與權威，偵測漂移並重生

**主防線刻意不是攔截式閘門。** Claude Code 的 Edit/Write、Obsidian 都是直接寫檔案系統、不經過服務層——攔截在架構上就有洞。所以改成「偵測 + 自我修復」。
→ 知識點：**契約驅動解耦**

### 難題 1 — 一個守門空轉了四個月，沒有人知道

**現象**：檢索品質的回歸閘門（eval）存在、排程每次都跑、程式碼沒壞。但它從上線起**四個月沒有攔下過任何東西**。

**根因**：閘門的結果**沒有被算進紅燈計數**。它算完了，寫進 log，然後就沒有然後了。整條告警路徑從來不會被觸發。

**同型的還有三個**：`export --check` 只看標記不看內容、另一個檢查不進紅燈、hook 的掃描範圍不含 `_config/`。

**解法不是修那個閘門**，是把問題重新定義成：

> 每一條可能失敗的路徑，都要能回答一個問題：**「這裡失敗了，誰會知道？」**
> 答案如果是「沒有人」，這段程式碼就還沒寫完。

這條後來寫成專案的常駐規則，並且反過來查出更多同型缺陷。

**這裡有個更微妙的教訓**：新加的守門**第一次跑就接上告警出口是錯的**。一個沒事也亮紅燈的檢查，下一個人最合理的反應就是把它關掉——然後它連真的壞掉時也不會有人看。守門要先「證明自己不亂叫」才有資格叫。

---

### 難題 2 — ChromaDB 擁有權，同一個形狀在四個層次重演

**現象**：帶 filter 的向量查詢持續回 `Error finding id`，而且只打得中一個分類。

往下追四層，**每一層都是同一個形狀**：

| 層 | 守衛 | 它以為自己在守 | 它實際在守 |
|---|---|---|---|
| 1 | stdio 用具名 mutex、api 用埠探測 | DB 擁有權唯一性 | 各自的傳輸層，兩道互不相見 |
| 2 | 唯一性判定寫在 `_start_api()` | 開 DB 之前 | 開 DB **之後**（`_bootstrap()` 已經開了） |
| 3 | 殭屍清掃排除現役行程 | 比對命令列 `--mode api` | 打包版的 CommandLine **讀不到**，排除永不命中 |
| 4 | installer 以原使用者身分啟動 SSE | — | 缺 `runasoriginaluser`，提權啟動（第 3 層的上游） |

第 3 條最刺：log 直接寫著「已清除 1 個殭屍實例（父行程已死）：[29668]」，而 **29668 正在服務 8765**。殺它的是 AI 客戶端自己啟動 MCP 時跑的清掃程序。

**解法**：
- 改用共用鎖 `Global\VaultMcpDbOwner`——**鎖的名字要說出它守的是什麼**（DB 擁有權，不是傳輸層）
- 判定上移到開 DB 之前
- 清掃改 fail-closed：讀不到命令列就當作「可能是現役」，不殺
- stdio 恆為 bridge：SSE 不在就自己拉起並輪詢等待，讓 DB 擁有者由**行程角色**決定，而不是啟動時序

**第 3 條的證據全部來自這次才補的 `stdio-server.log`。** 在那之前 file handler 只掛在 api 分支，stdio 的失敗只進 stderr、被編輯器吞掉。那批持續失敗在既有 log 裡一行都沒有——不是沒發生，是沒地方寫。

---

### 難題 3 — 兩個只在打包版才發作的 bug

從原始碼跑都正常，所以測試全綠、開發時完全看不到。兩個都是**使用者實測撞出來的**：

1. **更新確認視窗掛在幾乎不會發生的事件上**
   Popup 只掛在 SSE server 首次連線，而 SSE 是開機自啟的常駐行程——實測服務中的行程已連續執行 11 小時。使用者說「我重開了但沒觸發」。

2. **狀態診斷工具在任何打包版上都是壞的**
   `diagnostics.schema.json` 從來沒有進 bundle。

**修 bug 花的時間遠少於驗證。而我在驗證階段把同一個形狀重演了三次**：

| # | 我以為 | 實際 |
|---|---|---|
| 1 | 新 exe 修好了 | 新 exe 的呼叫被轉給現役的舊服務——入口是新的，幹活的是舊的 |
| 2 | 測試通過了 | 測試根本沒執行，而我把 stderr 丟進 `/dev/null` |
| 3 | 路徑沒問題 | 我自己寫的錯誤處理吞掉了所有例外，導致第 2 點的路徑錯誤連我自己都查不出來 |

第 3 點掩蓋的是一個真 bug：兩支 exe **不在同一層**（安裝版差一層、開發版是兄弟目錄），第一版假設同層 → 在打包版上必定失敗。

> **沒有堅持用真實入口驗，這版會帶著一個「看起來修好了、實際還是不會跳」的東西出去。**

**這件事後來變成一個可斷言的機制**：每個產物帶 `build_id`，讓「我驗到的是不是我剛建的那份」不再靠記憶。**安裝後首次實戰就命中了**——這正是這個機制存在的理由。

---

### 難題 4 — 我自己寫的守門測試，永遠不會紅

同儕審查（Codex）抓到的，三個原始發現全部成立、一個都沒反駁掉。最刺的是這個：

```python
# 測試想守：所有排程任務都要有對應的 handler
def _registered_ids():
    # 用正則抓原始碼裡字面的 id="..."
    ...

assert _registered_ids() - handler_ids == set()
```

實際的註冊寫法是 `id=_Id`（**變數，不是字面字串**），所以 `_registered_ids()` 回傳**空集合**。

> **空集合減任何集合等於空集合。差集永遠是空的，測試永遠不會紅。**

更刺的是同一個檔案裡有另一條自檢，**卻只守了差集的右邊**。

**解法**：改讀真正的 `TASK_REGISTRY`（實測 16 vs 16），並補上守左邊的斷言。

**同一輪還抓到我的機械式改寫製造了新缺陷**：某個 TSX 檔有重複的物件 key，插入的值被下方原有的覆蓋。`tsc` 一行就抓到，**而我的正則測試全綠——因為它們只看每行第一個匹配**。已補上真正的 TypeScript 編譯檢查。

→ 知識點：**多模型同儕審查**

### 難題 5 — 升級凍結：官方預設值在安裝當天就死了

**現象**：發現既有使用者的行為跟新版不一致，即使他們裝了新版。

**根因**：安裝時對已存在的設定檔用 `skip-if-exists`。這在直覺上是對的（不要覆蓋使用者的修改），但它的長期後果是：

> **官方預設值在安裝當天被凍結。之後所有的行為修正，一輩子送不到既有使用者手上。**

**解法**：改用 Debian conffile 的三態模型——

| 情況 | 處置 |
|---|---|
| 使用者沒改過 | 直接更新成新的預設值 |
| 使用者改過、新版沒改 | 保留使用者版本 |
| 兩邊都改過 | 保留使用者版本，落一份新版在旁邊並告知 |

---

### 難題 6 — 供應鏈：兩顆 `.pyc` 真的出貨給人了

**現象**：某個目錄的 `__pycache__/` 下兩顆 `.pyc` **每次 build 都被整目錄遞迴打進 exe**。

三重失效：
1. 打包規則是「整個目錄遞迴收」，繞過了內容清洗管線
2. 那個目錄**不在 git 追蹤範圍**——`git status` 乾淨從來沒反映真相
3. 檢查腳本的 `-Check` 模式對它們視而不見

**實查已安裝的版本**，那兩顆確實在裡面。

**解法**：打包改為**允許清單**（`build_plan.py`），規則首次匹配、**沒有 catch-all**——一個未分類的檔案會讓 build 直接失敗。實測打包 96 檔、0 個 `.pyc`。

---

### 難題 7 — 自動學習管道對中文使用者近乎無效

**現象**：自動從對話萃取知識卡片的管道，送進去 4 則、只出 1 張。

**分析**：沒中的 3 則共通點是**整句都是中文**，命中的那則含 `PowerShell 5.1` / `UTF-8` 等英文詞。

**根因**：卡在 slug 化——中文轉 slug 後退化成無意義字串，於是**整則被丟棄**。816 則實測，**21.6% 是通過品質閘門之後才死在取名字這關**。

**這件事的嚴重性在於**：使用手冊剛剛才教人「寫的時候帶分隔符就會建卡」，但繁中使用者照做也大機率不會建出卡——而且跳過時只寫 log，沒有人會知道。

**解法**：slug 退化時以序號或雜湊補位，而不是整則丟棄。

## 五、它不是 demo — 真實使用與資料邊界

這套系統自 2026-04 起就是我**日常工作的一部分**，不是寫完就放著的專案。實際的使用場景：

| 場景 | 它做了什麼 |
|---|---|
| 動 legacy 原始碼之前 | **編碼守門自動注入**——非 UTF-8 檔案禁用一般讀寫工具，改用指定 code page 的原生 API |
| 寫程式前 | 召回該語言的編碼規範，以及過去在同類問題上踩過的坑 |
| 跨對話 / 跨機器 | 專案脈絡不中斷——上次卡在哪、為什麼那樣決定 |
| 事後 | 從實際犯的錯萃取成帶信心度的經驗卡片，下次同型情境自動提醒 |

### 也因為如此，資料邊界是先設計的

使用場景會接觸到專有資訊，所以三道邊界是**前置條件**，不是事後補的：

| 邊界 | 機制 |
|---|---|
| **隱私路由**（fail-closed） | 任務內容或來源路徑命中敏感關鍵詞時，**在派工前強制改用本機模型**——不管那個任務宣告要用哪個雲端服務。防的是無人值守的排程把東西自動送出去 |
| **去識別化閘門** | 任何對外產出前的掃描層。規則**自帶測試樣本**讓新增規則自動取得覆蓋；**掃 git 全歷史**——因為識別字刪掉再 commit，歷史裡那一版仍然讀得到 |
| **內容分區** | 依**所有權**分區。敏感區不進索引、不進版控；寫入公司資產時另有一套規則，禁止帶入任何個人系統的名稱與路徑 |

### 真實使用換來了什麼

**真實使用者產生的回報，是任何測試都生不出來的。**

最有代表性的一句是「**我重開了但沒觸發**」——它揭露了一個只在打包版發作的缺陷：更新提示掛在一個幾乎不會發生的事件上（常駐服務的首次連線），而它從原始碼跑永遠正常。

同一族的還有「你剛剛觸發的更新不是正常的流程吧？正常我應該可以按確認才對？」——那次我用內部指令把更新做完了，但使用者要看的是**那條路走起來長什麼樣**，不是「更新完成」這個狀態。

> 這兩句話都不可能出現在測試裡。**一個沒有真實使用者的系統，永遠不會知道自己的哪一條路徑是壞的。**

## 六、面試怎麼講

**如果只有 60 秒**：
> 我做了一個把個人知識庫變成 AI 長期記憶的 RAG 後端，用 MCP 協定暴露 25 個工具，支援四種部署形態。技術上是 BM25 加向量的混合檢索再做時間衰減重排。但這個專案真正教會我的不是 RAG——是**「沉默的失敗」**：我在裡面抓到十幾個「機制存在、但掛在錯的地方、而且失敗不會叫」的缺陷，包括一個空轉了四個月的品質閘門，和一個因為差集永遠是空集合所以永遠不會紅的守門測試。這讓我養成一個習慣：寫任何可能失敗的路徑時，先回答「這裡失敗了誰會知道」。

**如果對方追問「你怎麼確保品質」**：
> 三層。第一層是測試，2,397 個，但我不信任「測試綠」——所以第二層是**突變驗證**：故意注入違規，確認測試真的會紅。第三層是**跨模型同儕審查**，我把實作送給另一個模型審，單執行緒迭代到它給 APPROVED 為止。最近一次六輪，抓到三個真問題，**沒有一個是測試抓到的**。

**如果對方問「最難的部分」**：
> 不是任何一個技術點，是**驗證的方向性**。我有一次修一個 bug，修完驗證，連續三次以為修正失敗——第一次驗到的是舊版、第二次測試根本沒執行、第三次是我自己寫的錯誤處理吞掉了例外，導致我連自己的錯都查不出來。這之後我做了一個 `build_id` 機制，讓「我驗到的是不是我剛建的那份」變成可斷言的事實而不是靠記憶。
