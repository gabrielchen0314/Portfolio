## 一、解什麼問題

跟 AI 協作最大的浪費，是每次都要重新解釋一遍脈絡。我用什麼命名慣例、這個專案卡在哪、上次那個坑是怎麼解的。

市面上的作法是把知識塞進 prompt，但塞不下。或者做成 RAG 讓 AI 自己查，但 **AI 不會主動想到要查**。

所以這個系統的定位不是「一個能搜的知識庫」，而是：

> **一個讓 AI 在對話開始的第一次呼叫就自動拿到對的脈絡的系統。**

知識以純 Markdown 存在檔案系統（Obsidian 可讀、grep 可搜、git 可版控），索引進 ChromaDB，透過 MCP 協定暴露成工具面給任何支援 MCP 的 AI 客戶端。

## 二、架構

> 2026-04 到 09 月，這套系統是**單一 repo** 的 AI Memory Vault：記憶、收工、報告、排程、Agent 任務全部在同一個引擎裡。
> 2026-09 起拆成三個產品，並改名 Espalio。下面描述的是拆分後的現況，拆分本身見〈減法計畫〉。

### 三層，三個 repo

| 層 | 產品 | 做什麼 |
|---|---|---|
| ① 記憶核心 | **Espalio Memory** | 記憶的寫入、存放、檢索、送到 AI 面前：<!--m:ai_memory_vault.mcp_tools_exposed-->8<!--/m--> 支 MCP 工具、索引、內嵌維護定時器、自檢更新。只裝它也能完整使用記憶功能 |
| ② 工作流插件 | **Espalio Workflow** | 我自己的工作流（收工、報告、排程、Agent 任務、多模型辯論）與編輯器轉接器。獨立行程，**只透過 MCP 存取核心** |
| ③ 平台 | **Espalio**（Rust ＋ Tauri） | Windows 常駐主控台：看護各配件行程、執行它們在 manifest 宣告的排程，並把所有配件的 MCP 工具聚合成編輯器只需接一次的 `espalio` 入口；依風險等級放行、逐次確認或不暴露，每次呼叫寫稽核 |

核心兩條硬約束：

1. **核心不呼叫 LLM。** 嵌入它的 AI 就是大腦，由它判斷該記什麼；核心的「成長」全是機械式的（信心度事件、時間衰減、晉升標記、reindex）
2. **每個工具輸出都有 token 預算**，超過就截斷並明說截了什麼

依賴方向由測試以 AST 掃描守住：核心不得 import 插件，沒有例外。

### 核心內部分層

```
Transport    main.py 依 --mode 路由到 stdio / SSE / CLI
MCP Tools    mcp_app/tools/ — 21 支工具：8 支核心（recall/read/remember/update/forget/rename/context/sync）
             ＋ 10 支舊名隱藏相容一個版本（呼叫會寫棄用紀錄）＋ 3 支運維類預設關閉
Library API  vault_core/ — 對外的程式庫介面，8 支工具都是它的薄包裝
Services     services/ — VaultService 門面、Instinct、PromotionScanner、Maintenance、Doctor、Updater
Core         core/ — Indexer、Retriever、Embeddings、VectorStore、Migrations
```

分層同樣由 import-linter 機器強制：`core` 不依賴上層，`services` 不依賴 `mcp_app`／`cli`。

### 五種部署形態，同一份程式碼

| 形態 | 傳輸 | 用途 |
|---|---|---|
| Python venv | stdio MCP | 開發 |
| PyInstaller exe + Inno Setup 安裝檔 | stdio + SSE | 一般使用者（124.4 MB 安裝檔） |
| Docker | SSE (8765) | 遠端／跨機器 |
| 常駐 SSE 服務 | SSE (8765) | 多個編輯器共用同一個核心 |
| Tauri 桌面 UI | HTTP → SSE | 進行中 |

多形態是後面一整節難題的來源。同一份程式碼在 frozen 模式下的行為跟從原始碼跑不一樣，而測試只跑後者。

### 檢索管線

```
query
  ├─ BM25 稀疏檢索 ─┐
  └─ 向量檢索 ──────┴─ 加權 RRF 融合：score = w / (rank + c)，c = 5
        ↓
   composite scoring：relevance × recency × type × focus
     · recency 是有界乘數 (1−w) + w × decay，w = 0.3、半衰期 90 天
     · 規則與技能這類常青文件不受時間衰減
        ↓
   top_k 結果
```

兩側權重由設定決定（現行 BM25 0.5、向量 0.6）。Embedding 模型 `paraphrase-multilingual-MiniLM-L12-v2`（多語、CPU 可跑）。
RRF 的 `c` 原本沿用函式庫預設 60，2026-09 拆出不用於守門的調參集之後才改成 5，見難題 1 之後的〈一個刻意延後的參數〉。
→ 知識點：混合檢索

### 一次往返拿完脈絡：`context`

冷啟動的 AI（SubAgent、外部工具）繼承不到主對話的記憶注入。核心的 `context` 工具在 token 預算內一次回傳：使用者指定釘選的筆記，加上與當前任務相關的高信心經驗卡片。

Agent 定義、規則全文、Skill 清單這類**工作流的東西不在這裡**，由插件組裝。這條界線就是減法計畫畫出來的。
→ 知識點：MCP 工具面設計

### 減法計畫：把「我的工作流」從記憶核心拆出去（2026-09）

到 9 月，引擎裡已經長出收工、日週月報、排程器、Agent 任務、多模型辯論、編輯器設定投影……全部和記憶共用同一個行程、同一份設定。結果是任何人想用「記憶」，都得連我的個人工作流一起裝。

拆分的判準只有一條：

> 少了它，記憶還能被**寫進去、存好、找得到、送到 AI 面前**嗎？
> 是這四個動作之一 → 留在核心；其餘 → 工作流插件。

照這條切下去，核心的工具從 29 支收斂到 8 支常用動詞，排程器、收工流程和編輯器轉接器都搬到插件 repo。插件不能直接打開向量庫，要寫檔案就先取核心的檔案鎖，寫完再呼叫核心的 `sync` 收尾。

拆的過程刻意不一次切斷，**每一步都留得住回頭路**：

- 舊工具名保留一個版本，在 `tools/list` 隱藏，但每次呼叫都會寫棄用紀錄，看得到還有誰在用
- 插件指令在過渡期仍可經由核心轉發；等排程、腳本和 hook 範本都確認不再走核心（有測試掃三個 repo）才拆掉轉發，之後誤用只會印出該改用的插件指令並以非零碼結束
- 核心原本會把規則與 hook 資產「落地」到使用者知識庫，並用 reconciler 偵測漂移、自我修復（v3.26.0 的控制平面設計）。這整套連同它的 manifest 一起移給插件，現在**核心不往知識庫寫任何內容**

拆完之後，「核心不得依賴插件」從一條文件裡的約定，變成 AST 掃描的測試，而且沒有例外。
→ 知識點：契約驅動解耦

### 難題 1 — 一個守門空轉了四個月，沒有人知道

現象：檢索品質的回歸閘門（eval）存在、排程每次都跑、程式碼沒壞。但它從上線起**四個月沒有攔下過任何東西**。

根因：閘門的結果沒有被算進紅燈計數。它算完了，寫進 log，然後就沒有然後了。整條告警路徑從來不會被觸發。

同型的還有三個：`export --check` 只看標記不看內容、另一個檢查不進紅燈、hook 的掃描範圍不含 `_config/`。

解法不是修那個閘門，是把問題重新定義成：

> 每一條可能失敗的路徑，都要能回答一個問題：**「這裡失敗了，誰會知道？」**
> 答案如果是「沒有人」，這段程式碼就還沒寫完。

這條後來寫成專案的常駐規則，並且反過來查出更多同型缺陷。

這裡有個更微妙的教訓：新加的守門，第一次跑就接上告警出口是錯的。一個沒事也亮紅燈的檢查，下一個人最合理的反應就是把它關掉，然後它連真的壞掉時也不會有人看。**守門要先證明自己不亂叫，才有資格叫。**

### 一個刻意延後的參數

閘門接上之後，它量出的第一件有意思的事跟它自己有關。

RRF 融合 `score = w / (rank + c)` 的 `c` 從來沒有被指定，默默沿用函式庫預設 60。60 是為「數百筆的排序清單」設計的，而這裡每一側只取 5～20 筆：rank 1 與 rank 10 的分母只差 61 對 70，權重比 1.5 直接輾過名次。融合退化成「權重大的那一側說了算」。實測有一題 BM25 把正確答案排第 1、向量側排第 13，而混合檢索的輸出**與純向量逐位相同**。

把 `c` 改成 5，同一組題目的 recall@5 從 0.690 升到 0.786。但我**當下沒有改**：那組題目同時是回歸閘門的量尺，拿它調參，等於把參數調到讓閘門好看，之後那道閘門就再也證明不了「沒有退化」。所以那次只做一件事：把 60 從隱含預設變成程式碼裡明寫的常數，寫清楚它為什麼是 60、改它的代價是什麼。

2026-09-03，我決定接受代價：改成 `c = 5`，並重新校準閘門下限。隔天把題庫從 42 題擴充到 84 題，拆成 train 與 test 兩半：**調參只看 train，閘門只守 test**。改參數本身可以接受，要補上的是讓下一次調參不再污染量尺的機制。

但這個機制是**事後**才補上的：`c = 5` 是在拆分之前的 42 題上選的，其中 20 題落在現在的 test split（共 40 題）。所以 test 對這個值並不是完全沒見過，引用 test 的數字時這句要一起講。之後再動它，只准看 train。

### 難題 2 — ChromaDB 擁有權，同一個形狀在四個層次重演

現象：帶 filter 的向量查詢持續回 `Error finding id`，而且只打得中一個分類。

往下追四層，**每一層都是同一個形狀**：

| 層 | 守衛 | 它以為自己在守 | 它實際在守 |
|---|---|---|---|
| 1 | stdio 用具名 mutex、api 用埠探測 | DB 擁有權唯一性 | 各自的傳輸層，兩道互不相見 |
| 2 | 唯一性判定寫在 `_start_api()` | 開 DB 之前 | 開 DB **之後**（`_bootstrap()` 已經開了） |
| 3 | 殭屍清掃排除現役行程 | 比對命令列 `--mode api` | 打包版的 CommandLine **讀不到**，排除永不命中 |
| 4 | installer 以原使用者身分啟動 SSE | — | 缺 `runasoriginaluser`，提權啟動（第 3 層的上游） |

第 3 條最刺：log 直接寫著「已清除 1 個殭屍實例（父行程已死）：[29668]」，而 29668 正在服務 8765。殺它的是 AI 客戶端自己啟動 MCP 時跑的清掃程序。

解法：

- 改用共用鎖 `Global\VaultMcpDbOwner`。鎖的名字要說出它守的是什麼，是 DB 擁有權不是傳輸層
- 判定上移到開 DB 之前
- 清掃改 fail-closed：讀不到命令列就當作「可能是現役」，不殺
- stdio 恆為 bridge：SSE 不在就自己拉起並輪詢等待，讓 DB 擁有者由行程角色決定，而不是啟動時序

第 3 條的證據全部來自這次才補的 `stdio-server.log`。在那之前 file handler 只掛在 api 分支，stdio 的失敗只進 stderr、被編輯器吞掉。那批持續失敗在既有 log 裡一行都沒有。**不是沒發生，是沒地方寫。**

### 難題 3 — 兩個只在打包版才發作的 bug

從原始碼跑都正常，所以測試全綠、開發時完全看不到。兩個都是使用者實測撞出來的：

1. **更新確認視窗掛在幾乎不會發生的事件上**
   Popup 只掛在 SSE server 首次連線，而 SSE 是開機自啟的常駐行程。實測服務中的行程已連續執行 11 小時。使用者說「我重開了但沒觸發」。

2. **狀態診斷工具在任何打包版上都是壞的**
   `diagnostics.schema.json` 從來沒有進 bundle。

修 bug 花的時間遠少於驗證。而我在驗證階段把同一個形狀重演了三次：

| # | 我以為 | 實際 |
|---|---|---|
| 1 | 新 exe 修好了 | 新 exe 的呼叫被轉給現役的舊服務。入口是新的，幹活的是舊的 |
| 2 | 測試通過了 | 測試根本沒執行，而我把 stderr 丟進 `/dev/null` |
| 3 | 路徑沒問題 | 我自己寫的錯誤處理吞掉了所有例外，導致第 2 點的路徑錯誤連我自己都查不出來 |

第 3 點掩蓋的是一個真 bug：兩支 exe 不在同一層（安裝版差一層、開發版是兄弟目錄），第一版假設同層，在打包版上必定失敗。

> **沒有堅持用真實入口驗，這版會帶著一個「看起來修好了、實際還是不會跳」的東西出去。**

這件事後來變成一個可斷言的機制：每個產物帶 `build_id`，讓「我驗到的是不是我剛建的那份」不再靠記憶。安裝後首次實戰就命中了，這正是這個機制存在的理由。

### 難題 4 — 我自己寫的守門測試，永遠不會紅

同儕審查（Codex）抓到的，三個原始發現全部成立、一個都沒反駁掉。最刺的是這個：

```python
# 測試想守：所有排程任務都要有對應的 handler
def _registered_ids():
    # 用正則抓原始碼裡字面的 id="..."
    ...

assert _registered_ids() - handler_ids == set()
```

實際的註冊寫法是 `id=_Id`，是變數不是字面字串，所以 `_registered_ids()` 回傳空集合。

> **空集合減任何集合等於空集合。差集永遠是空的，測試永遠不會紅。**

更刺的是同一個檔案裡有另一條自檢，卻只守了差集的右邊。

解法：改讀真正的 `TASK_REGISTRY`（實測 16 vs 16），並補上守左邊的斷言。

同一輪還抓到我的機械式改寫製造了新缺陷。某個 TSX 檔有重複的物件 key，插入的值被下方原有的覆蓋。`tsc` 一行就抓到，而我的正則測試全綠，因為它們只看每行第一個匹配。已補上真正的 TypeScript 編譯檢查。

→ 知識點：多模型同儕審查

### 難題 5 — 升級凍結：官方預設值在安裝當天就死了

現象：發現既有使用者的行為跟新版不一致，即使他們裝了新版。

根因：安裝時對已存在的設定檔用 `skip-if-exists`。這在直覺上是對的，不要覆蓋使用者的修改，但它的長期後果是：

> **官方預設值在安裝當天被凍結。之後所有的行為修正，一輩子送不到既有使用者手上。**

解法：改用 Debian conffile 的三態模型。

| 情況 | 處置 |
|---|---|
| 使用者沒改過 | 直接更新成新的預設值 |
| 使用者改過、新版沒改 | 保留使用者版本 |
| 兩邊都改過 | 保留使用者版本，落一份新版在旁邊並告知 |

---

### 難題 6 — 供應鏈：兩顆 `.pyc` 真的出貨給人了

現象：某個目錄的 `__pycache__/` 下兩顆 `.pyc` 每次 build 都被整目錄遞迴打進 exe。

三重失效：

1. 打包規則是「整個目錄遞迴收」，繞過了內容清洗管線
2. 那個目錄不在 git 追蹤範圍，`git status` 乾淨從來沒反映真相
3. 檢查腳本的 `-Check` 模式對它們視而不見

實查已安裝的版本，那兩顆確實在裡面。

解法：打包改為**允許清單**（`build_plan.py`），規則首次匹配、沒有 catch-all。一個未分類的檔案會讓 build 直接失敗。實測打包 96 檔、0 個 `.pyc`。

### 難題 7 — 自動學習管道對中文使用者近乎無效

現象：自動從對話萃取知識卡片的管道，送進去 4 則、只出 1 張。

分析：沒中的 3 則共通點是整句都是中文，命中的那則含 `PowerShell 5.1` / `UTF-8` 等英文詞。

根因：卡在 slug 化。中文轉 slug 後退化成無意義字串，於是整則被丟棄。816 則實測，**21.6% 是通過品質閘門之後才死在取名字這關**。

這件事的嚴重性在於，使用手冊剛剛才教人「寫的時候帶分隔符就會建卡」，但繁中使用者照做也大機率不會建出卡。而且跳過時只寫 log，沒有人會知道。

解法：slug 退化時以序號或雜湊補位，而不是整則丟棄。

## 五、它不是 demo — 真實使用與資料邊界

這套系統自 2026-04 起就是我日常工作的一部分，不是寫完就放著的專案。實際的使用場景：

| 場景 | 它做了什麼 |
|---|---|
| 動 legacy 原始碼之前 | **編碼守門自動注入**。非 UTF-8 檔案禁用一般讀寫工具，改用指定 code page 的原生 API |
| 寫程式前 | 召回該語言的編碼規範，以及過去在同類問題上踩過的坑 |
| 跨對話 / 跨機器 | 專案脈絡不中斷：上次卡在哪、為什麼那樣決定 |
| 事後 | 從實際犯的錯萃取成帶信心度的經驗卡片，下次同型情境自動提醒 |

### 也因為如此，資料邊界是先設計的

使用場景會接觸到專有資訊，所以三道邊界是**前置條件，不是事後補的**：

| 邊界 | 機制 |
|---|---|
| **隱私路由**（fail-closed） | 任務內容或來源路徑命中敏感關鍵詞時，在派工前強制改用本機模型，不管那個任務宣告要用哪個雲端服務。防的是無人值守的排程把東西自動送出去 |
| **去識別化閘門** | 任何對外產出前的掃描層。規則自帶測試樣本，讓新增規則自動取得覆蓋。掃描涵蓋 git 全歷史，因為識別字刪掉再 commit，歷史裡那一版仍然讀得到 |
| **內容分區** | 依所有權分區。敏感區不進索引、不進版控。寫入公司資產時另有一套規則，禁止帶入任何個人系統的名稱與路徑 |

### 真實使用換來了什麼

真實使用者產生的回報，是任何測試都生不出來的。

最有代表性的一句是「我重開了但沒觸發」。它揭露了一個只在打包版發作的缺陷：更新提示掛在一個幾乎不會發生的事件上，也就是常駐服務的首次連線，而它從原始碼跑永遠正常。

同一族的還有「你剛剛觸發的更新不是正常的流程吧？正常我應該可以按確認才對？」那次我用內部指令把更新做完了，但使用者要看的是那條路走起來長什麼樣，不是「更新完成」這個狀態。

> 這兩句話都不可能出現在測試裡。**一個沒有真實使用者的系統，永遠不會知道自己的哪一條路徑是壞的。**
