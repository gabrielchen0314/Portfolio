# 02 · Remote AI Task Platform

> **讓 AI CLI 以低權限帳號、非互動方式在背景安全執行任務。**
> Python · SQLite (WAL) · Discord.py · Windows API (LogonUser / Job Object)
> 2026-07 起，Phase 1B 完成｜528 tests passed

---

## 一、解什麼問題

我想在不坐在電腦前的時候，也能讓 AI 幫我做事——手機上發一句話，家裡的機器就去執行。

聽起來像個小工具。但一旦你認真對待「AI 要在我不看著的時候、以我的身分、在我的機器上執行東西」這句話，問題立刻變成：

> **在什麼都可能出錯的前提下，怎麼讓每一步都留下事後查得出來的痕跡？**

這個專案的重心因此不在功能，在**安全邊界與稽核**。

---

## 二、架構

```
Discord / CLI / Dashboard          ← 三個入口
        ↓
   Router（意圖路由 + 風險分層）
        ↓
   Platform.submit()               ← 唯一入隊點，不得繞過
        ↓
   五段稽核：received → routed → enqueued → completed → notified
        ↓
   SQLite 佇列（WAL + thread-local + BEGIN IMMEDIATE）
        ↓
   Worker（持有 OS 檔案鎖者才啟動）
        ↓
   Plugin Registry
     ├─ in_process     唯讀外掛（載入期硬性禁止寫入）
     └─ out_of_process 寫入型外掛，以低權限帳號 spawn
```

### 幾個刻意的設計

**`request_id` 貫穿五段稽核。**
原本前兩段寫在 job id 生成之前，只有訊息雜湊；第三段起才有 job id 卻沒有事件型別。結果是**同指令同參數的兩次請求無從分辨**，串鏈只能靠時間相近去猜。加入入口生成的 `request_id` 並持久化到記錄，六種事件全帶。

**低權限外掛以獨立帳號執行。**
建立本機標準帳號，父行程用 SID 向 OS 證明子行程身分。啟動前有兩層 preflight：帳號存在、**且密碼可讀**（原本「帳號已設、密碼沒設」會通過閘門，拖到 spawn 才炸）。

**`delivered=true` 的定義是「寫進 outbox」而不是「瀏覽器看到了」。**
否則使用者關掉分頁就會讓任務永遠停在「未通知」。定義要落在系統控制得了的地方。

→ 知識點：**最小權限的工程落地**

## 三、開發難題與解法

### 難題速查

| # | 難題 | 根因形狀 | 知識點 |
|---|---|---|---|
| 1 | dry-run 變成實彈執行 | 舊版行程從共用佇列搶走 job | **沉默的失敗** |
| 2 | 稽核有三條路徑一個字都不寫 | 只有例外分支會留痕 | **沉默的失敗** |
| 3 | 模型選擇可被「降級攻擊」 | 判準取自不可信來源 | **Prompt Injection 與信任邊界** |
| 4 | 安全守衛的條件過窄，推翻整份論證 | 單向蘊含被當成雙向 | **fail-closed** |
| 5 | 一個階段閘門在字面上永遠無法通過 | 前提列錯了階段 | — |
| 6 | 審查過程本身洩漏了密碼 | 沙箱範圍給太寬 | **最小權限** |

---

### 難題 1 — dry-run 變成實彈：舊版行程搶走了 job

**現象**：送一筆標記為 dry-run 的動作，稽核鏈停在 `enqueued`，後面兩段沒有。看起來像「卡住了」。

**真相比卡住嚴重得多**：一個**執行中的舊版 Gateway** 從共用的 SQLite 佇列搶走了這個 job。而舊版的程式碼**不認得 `dry_run` 這個欄位**——

> **它真的執行了。**

稽核之所以「少兩段」，是因為舊碼寫的完成事件裡沒有 `request_id`，串不起來。

**同型事故在這個專案發生過兩次**（另一次是外掛看起來壞掉，實際是舊行程的 worker 搶到號，而它的 registry 裡沒有那個外掛）。

**解法是兩道獨立的守衛，各擋不同的東西**：

| 守衛 | 擋什麼 | 為什麼另一道擋不了 |
|---|---|---|
| OS 檔案鎖（worker 啟動**之前**取得） | 同版本共存 | — |
| 行程掃描 | **跨版本**共存 | 舊碼不知道有鎖，自然不會去搶 |

**掃描失敗一律當作「有」**——一個會默默失效的偵測，等於從來沒裝過。

兩道都過才開放動作入口。**用突變測試驗證**：移除任一道，對應的測試立刻變紅。

**為什麼用 OS 檔案鎖而不是 pid 檔**：Windows 上 `os.kill(pid, 0)` 會**真的殺掉行程**；pid 檔躲不掉殘鎖與 pid 重用；而檔案鎖在行程崩潰時由核心自動釋放。

**衍生的操作規則**：升級後必須重啟常駐服務。而且驗證方式不是「確認行程還在」，是**確認新行程持有那個鎖**（鎖檔無法被獨占開啟）——後者才證明守衛真的生效。

---

### 難題 2 — 稽核有三條路徑，一個字都不寫

**現象**：通知送不出去的時候，稽核裡看不到。

**根因**：只有拋例外的分支會寫稽核。另外兩條——「沒有設定發送器」與「發送函式回傳 False」——**一個字都不寫**。

**更糟的是**：既有測試正是用「發送回傳 False」來模擬斷線。

> **測試本身在驗證一條沉默的路徑。**

**解法**：三條路徑全部留痕，並且把 `pending` 欄位的語意改成誠實反映「會不會被重撈」（三條都會，所以一律 True），失敗種類另用 `failure_kind` 區分。

**第一版我寫 `pending=False` 是假的**——稽核宣稱不會再試而實際上會再試，**比沒有這個欄位更糟**：沒有欄位只是資訊不足，錯的欄位會讓人做出錯的決定。

---

### 難題 3 — 模型選擇的「降級攻擊」與「燒錢攻擊」

**背景**：路由器要決定一個請求用便宜模型還是強模型。第一版依「使用者輸入的難度」判斷。

**兩個攻擊面**：

| 攻擊 | 手法 | 後果 |
|---|---|---|
| 降級攻擊 | 把敏感操作包裝成看起來很簡單的輸入 | 用便宜模型執行敏感操作 |
| 燒錢攻擊 | 刻意製造高難度輸入 | 拉高成本 |

**共同根因**：判準取自**使用者可操控的來源**。

**解法**：改依外掛 manifest 宣告的 `is_readonly` 屬性分層——那是**可信來源**，使用者改不了。

**同一輪還修掉兩個東西**：
- 成本價表把最貴模型的單價套用到所有模型，導致便宜模型的成本被高估約 5 倍——**這個 bug 會反轉決策結論**
- 分類器的建構時機早於外掛註冊，造成 fail-open 陷阱（分類器拿到空的 registry，於是什麼都判成低風險）

---

### 難題 4 — 守衛的條件過窄，會推翻整份論證

這是同儕審查抓到的，值得單獨講，因為它是**論證與實作不一致**的典型。

**我的提案論證**：這三條風險「只存在於 `out_of_process` 外掛」。
**我的守衛實作**：只檢查 `is_readonly`。

審查者去核對載入期的檢查，發現那是**單向蘊含**——它只約束 `in_process`。因此：

```
out_of_process + is_readonly:true + requires_llm:true + allowed_cli:[...]
```

這個組合**可以通過驗證，並命中全部三條風險路徑**。我的論證是對的，我的守衛沒有實現那個論證。

**解法**：四個條件同時檢查。並且**測試必須使用 `out_of_process` fixture**——用 `in_process` 寫的違規案例在載入期就被擋掉了，**測不到這個守衛**。

> 這件事的一般化：**寫測試時要確認那條路徑真的走得到你要守的地方**，否則測試綠燈只證明別的東西攔下了它。

---

### 難題 5 — 一個階段閘門在字面上永遠無法通過

**現象**：Phase 1C 的進場條件裡有三列，按字面「全綠才可開」，**這個階段永遠無法進場**。

**根因**：那三列其實是下一階段（1D）的前提，被誤列進來了。其中一列是「CLI 白名單沒有強制力」——那是 CLI 產品的**既成事實，架構上不會轉綠**，也正是我們自建 broker 的理由。

**解法**：把表拆成 1C / 1D 兩份。收斂後 Phase 1C 只剩一列未滿足：真實流量的路由準確率——而**唯一的來源是真的有人用它**，測例無法取代。

**這件事的價值不在修好一張表**，在於：

> **當一個閘門在字面上不可能通過時，通常不是標準訂太高，是有東西被放錯了層。**

同一輪也讓我把「剩餘工作」誠實地重新分類：Phase 1B 剩下 3 項，**沒有一項是「還沒排到的程式碼」**——兩項阻塞在 IT 環境（CLI 是 per-user 安裝，低權限帳號讀不到），一項阻塞在「需要真人實際使用」。

---

### 難題 6 — 同儕審查過程本身洩漏了密碼

**事件**：把 repo 交給另一個模型做唯讀審查時，它的全文搜尋把 `.env` 裡的密碼明文印進了輸出。

**處置**：更換帳號密碼、更新設定、重跑自檢、重啟服務、全鏈複驗。

**根因判定要精確**：不是「密碼存在 `.env` 裡」——那是設計，而且 `.env` 在 `.gitignore`。根因是**把唯讀沙箱指向了整個 repo**，讓它 grep 得到。

**規則**：對此 repo 送審要避開全文搜尋。**權限邊界要跟著資料走，不是跟著行為的「危險程度」走**——唯讀也會洩漏。

**一個決策點的定案過程值得記錄**：原本要決定「轉成 Windows Service 還是維持排程器」。實測發現 AI CLI 與 Python 全都是 per-user 安裝，低權限服務帳號**完全存取不到**——這是結構性限制，與登入型態無關。於是一個 FAIL 的實驗結果，變成一個有決策效力的定案。

> **一個好的 spike，失敗時要能定案，而不是只能重試。**
