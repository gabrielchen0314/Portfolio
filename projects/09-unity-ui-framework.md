## 一、解什麼問題

一款手機 MMO，邏輯幾乎都寫在 Lua，C# 負責引擎橋接與效能敏感的元件。介面控制器超過 150 個，種類很雜：

| 介面類型 | 行為 |
|---|---|
| 全版 | 蓋住整個畫面，有上一頁堆疊 |
| 半版 | 蓋住一半，可以跟主介面並存 |
| 子介面 | 依附在另一個介面上，跟著它開關 |
| 常駐 | 主介面上的按鈕列、資源列 |

再加上教學引導、過場動畫、斷線重連、多種螢幕比例。

如果每個介面自己管自己，結果會是：誰蓋住誰說不清楚、上一頁回到錯的地方、關一個介面連帶把別人的子介面關掉。需要的是一套**所有介面都經過的地基**。

---

## 二、架構

```
UI 管理器（Lua）
  ├─ 分層：全版堆疊 / 半版表 / 一般表，各自計算繪製順序（Order）
  ├─ 開啟流程：動態載入 → 準備 → 移入攝影機可見範圍 → 開啟完成回呼
  ├─ 子介面控制：介面宣告「我開啟時要顯示 / 隱藏哪些介面」
  └─ 解析度：初始化與解析度變更時更新 CanvasScaler 參考解析度
        │
介面控制器基底（UIControllerBase）
  └─ 生命週期、語言設定重設、動畫設定、可見性效果
        │
元件（C# + Lua）
  ├─ 無限捲軸 ScrollView：只產生看得到的格子，捲動時回收重用
  ├─ 邊界元件：安全區、平板比例、非 16:9 螢幕的縮放
  ├─ 按鈕：群組按鈕與開關按鈕的狀態機（選取 / 懸停 / 停用互斥與恢復）
  └─ 標題列、分頁、下拉選單等共用元件
        │
資料層
  ├─ DataMgr / DataModel：靜態資料與事件資料模型
  ├─ 串檔讀取：分段非同步讀取
  └─ 本機存檔、下載檔管理、JSON 管理
```

上面列的介面控制器基底、無限捲軸、邊界元件、按鈕元件、資料層各管理器，最初的新增者是我。UI 管理器在專案生命週期內被修改 537 次，其中 222 次是我（41%，以 git log 計）。

## 三、開發難題與解法

### 難題 1：介面開啟改成非同步之後，開到一半的介面會被誤關、會重疊

背景：早期介面開啟是同步的。2025 年把開啟流程改成協程，分段執行。

現象：改完之後出現兩類問題。一個介面還在開啟中，使用者點了關閉，結果它稍後又自己出現；或兩個全版介面疊在一起，上一頁回到錯的地方。

根因：同步時，「開」是一個瞬間完成的動作，不需要能被取消。改成非同步之後，「開」變成一段時間，而原本的關閉流程**不知道有一個正在跑的開啟**：

- 關閉沒有停止開啟中的協程，所以它跑完後照樣把介面顯示出來。
- 關閉沒有把介面從全版堆疊移除，堆疊裡留下一筆已經關掉的介面。
- 排隊等待開啟的佇列沒有去重，同一個介面可以被排進去兩次。

解法：

```
關閉介面時:
    停止該介面的開啟協程（新增開啟協程的關閉介面）
    若是全版介面: 從全版堆疊移除
排隊開啟時:
    佇列已包含同一介面 → 不再加入
```

> 同步改非同步，最容易漏的不是「開」，是「開到一半時的關」。
> 每一個變成「一段時間」的動作，都要有對應的取消，而且所有會終止它的路徑都要知道這件事。

---

### 難題 2：同一個值有兩條算法，介面數量多時就算錯

現象：同時開啟的介面超過一定數量後，新介面的繪製順序算錯，被別的介面蓋住。

根因：繪製順序（Order）有兩個地方在算。一個是介面正式加入順序表之後；另一個是「還沒加入、先預估它會排第幾」。預估路徑沒有區分半版與一般介面，而開啟流程中有程式在介面還沒正式加入時就去讀它的 Order，拿到的是預估值。

解法：Order 計算收斂成一個統一介面，預估時也依介面類型走同一套規則；另外提供「取得某介面目前 Order」的查詢，取代各處自己讀欄位。

> 同一個值只要有兩條算法，遲早會分岔，而分岔通常發生在邊界條件下，平常測不到。

---

### 難題 3：子介面偶爾被不正確地關閉，只在打包後的執行檔出現

現象：主介面上的某些附屬介面，在特定操作順序後消失。編輯器內重現不了，只有打包後的版本偶爾出現。

這類問題靠讀程式碼很難找，因為「關閉子介面」的呼叫點很多，任何一個介面的關閉流程都可能連帶關掉別人的子介面。

做法：不猜，讓系統自己說出是誰關的。在除錯版加上兩個追蹤點：

```
於 關閉介面:
    若 被關閉的介面控制了主介面的子介面:
        記錄 呼叫來源（檔案與行號，取呼叫堆疊上一層）
於 停止開啟協程:
    若 目標是主介面的子介面:
        記錄 呼叫來源
```

追蹤只在除錯版開啟，正式版沒有額外成本。

> 這一節要講的是取證手法，不是根因。當呼叫點多到讀不完，就換成讓呼叫點自己報名。

→ 知識點：透過真實入口驗證

### 難題 4：螢幕比例不只兩種

現象：介面在 16:9 與 21:9 上正常，但在 4:3 平板與其他比例上元件跑出邊界或被裁掉。另外發現每開一個介面就重設一次 CanvasScaler 的參考解析度。

解法：

1. 邊界元件改成依實際比例計算縮放，對 4:3 等需要調高度的比例另外設定元件縮放比；邊界元件的更新從每幀 Update 改成委派通知。
2. 參考解析度只在 UI 管理器初始化與解析度設定變更時更新一次，不再跟著每次開啟介面。

第二點是典型的「功能正確、但做了太多次」：結果沒錯，所以不會有人回報，但它讓每次開介面都多做一件不必要的事。

---

### 難題 5：串檔讀取讓啟動卡住

背景：遊戲的靜態資料由企劃表格轉出的串檔提供，數量多、讀取集中在啟動階段。

做法分三步：

1. 2024 年把串檔讀取改成協程分段讀取。
2. 2025 年把整個串檔初始化流程統一改成協程，並加入可中止與重設的旗標。
3. 2026 年讓讀取失敗時直接報出來源檔名。原本只會說「讀取失敗」，要靠人去猜是哪一份檔案。

這一節沒有前後的啟動時間數字，因為當時沒有留下量測。這是我現在會先做的事：改效能之前先量。
